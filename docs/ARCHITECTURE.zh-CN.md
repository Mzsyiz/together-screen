# 架构设计

[English](ARCHITECTURE.md) | 简体中文

## 设计目标

Together Screen 面向小型可信群体：

- 10 个统一房间，每个房间最多 10 人；
- 每位参与者使用管理员创建的独立账号；
- 支持多人同时投屏；
- 低码率预览和点击后升级高清；
- 独立于屏幕清晰度的在线语音；
- 持久化文字聊天；
- 核心控制面可自托管，媒体可选用火山 RTC/WTN。

项目不试图替代大型会议系统或 SFU。

## 整体组件

```text
React 浏览器客户端
├── 房间和聊天界面
├── WebRTC 屏幕连接
├── WebRTC 语音连接
├── 火山 RTC / WTN 客户端
└── WebSocket 信令客户端
          │
          ▼
Fastify 业务服务器
├── 认证和会话
├── 房间成员和容量
├── WebSocket 信令转发
├── 画质请求与确认转发
├── 聊天 REST API
└── SQLite 持久化

STUN / coturn
└── NAT 地址发现和可选媒体中继
```

## P2P 媒体拓扑

P2P 模式使用网状拓扑：

```text
A 向 B 和 C 发送屏幕与语音
B 向 A 和 C 发送屏幕与语音
C 向 A 和 B 发送屏幕与语音
```

当房间有 `N` 人时，最多存在 `N × (N - 1)` 条有方向的媒体连接。编码和解码都在浏览器本地完成，业务服务器只承载信令和聊天。

这种方式对小型房间成本最低，但十人房全员共享时可达到 90 条方向性连接，发送端上传、浏览器编码和 TURN 出口带宽都会快速增加。十人房多人共享时应优先使用 RTC 或 WTN。

## 房间级媒体模式

每个固定房间持久化一个 `mediaMode`：

- `p2p`：现有浏览器 Mesh，必要时使用 STUN/TURN；
- `wtn`：火山引擎 WebRTC 传输网络的发布/订阅传输；
- `rtc`：火山引擎实时音视频 RTC，屏幕与麦克风独立发布。

只有管理员可以切换模式，而且只能在没有成员的房间中切换，避免中断正在传输的媒体。

系统提供 10 个统一房间，每个房间容量为 10 人，不再区分等级。每个空房间都可以由管理员独立选择自建 P2P/TURN、RTC 或 WTN。

客户端不再暴露任意分辨率、帧率和码率组合，而是使用以下标准参数档：

| 模式 | 目标参数 | 编码策略 | 使用场景 |
| --- | --- | --- | --- |
| 轻量 | 360p / 15 FPS / 0.8 Mbps | 平衡 | 最低带宽和弱网查看 |
| 流畅 | 720p / 10 FPS / 1.5 Mbps | 平衡 | 聊天、普通浏览、低带宽 |
| 标准 | 1080p / 15 FPS / 2.5 Mbps | 优先保持分辨率 | 默认推荐；办公、网页、文档、代码 |
| 高清 | 1080p / 30 FPS / 4 Mbps | 平衡 | 软件演示、动画、视频 |
| 超清 | 1440p / 30 FPS / 8 Mbps | 优先保持分辨率 | 高分辨率桌面、精细内容 |
| 游戏 | 1080p / 60 FPS / 8 Mbps | 优先保持帧率 | 游戏、快速运动 |
| 4K | 2160p / 30 FPS / 20 Mbps | 优先保持分辨率 | 4K 屏幕和足够上传带宽 |

所有房间开放相同的七种标准模式。实际发送码率仍由 WebRTC 拥塞控制动态调整。

### 火山 RTC 路径

RTC 房间使用两个浏览器端引擎：

- 主引擎：发布麦克风主流，以及所选清晰度的屏幕主屏流；共享系统声音开启时，主屏流附带系统音频。
- 预览引擎：使用独立的 `<userId>_preview` RTC 身份，只发布 360p / 15 FPS / 300 Kbps 屏幕视频，不包含任何音频。

观看者加入主引擎后自动订阅对方的预览身份。点击画面时先订阅主屏流，再取消预览，从而保留最近一帧并避免黑屏；取消聚焦时反向切回预览。系统声音只在高清主屏流中订阅，因此预览不会播放声音。

麦克风流使用 `publishStream(AUDIO)`，屏幕流使用 `publishScreen()`。清晰度变化只更新主屏编码配置，不离开 RTC 房间，也不重建麦克风发布。麦克风静音只调整主流采集音量，不影响屏幕系统声音。

Fastify 服务端按当前房间和用户签发短期 RTC Token，Token 绑定 RoomID 与 UserID。`RTC_APP_KEY` 只用于服务端 HMAC-SHA256 签名，浏览器不会获得。

### 火山 WTN 路径

WTN 房间把屏幕预览、屏幕高清和语音发布为三个独立媒体流：

```text
屏幕预览：<room>_<user>_screen_preview_<unique>
屏幕高清：<room>_<user>_screen_hd_<unique>
语音：    <room>_<user>_voice_<unique>
```

发布端为屏幕创建两个 WHIP 风格的 `RTCPeerConnection`：预览流约 360p / 15 FPS / 300 Kbps，高清流使用标准化场景自动生成的分辨率、帧率、码率和降级策略。预览流不依赖 Simulcast RID，因此不要求 WTN 应用支持 RID。观看者进入房间后会为每位共享者自动建立预览订阅并持续播放；点击后新建高清订阅并替换预览。取消聚焦或切换到其他画面时，观看者重新订阅预览，最近一帧只在订阅切换期间覆盖。

双流方案会让共享者额外上传约 300 Kbps 的预览流，但可以把“预览”和“高清”做成确定可切换的两条 StreamID，不受 WTN 单流层级能力影响。屏幕系统声音只随高清流发布；麦克风语音仍使用独立的单条语音流。

Fastify 服务端负责：

- 验证用户所在房间和媒体模式；
- 按屏幕预览、屏幕高清和语音分别登记最新 StreamID；
- 签发订阅资源前验证目标画质或语音流已经发布；
- 生成符合协议要求的 StreamID；
- 签发短期 HS256 WTN JWT；
- 只向浏览器返回 WTN URL 和 Token。

`WTN_APP_KEY` 永远只保存在服务端。停止或替换 WTN 发布者时会销毁媒体资源；预览结束或参与者离开时，订阅端会关闭自己的资源。

## 屏幕共享流程

### 开始共享

1. 共享者调用 `getDisplayMedia()`。
2. 浏览器应用分辨率和帧率限制。
3. 生成一份低分辨率启动快照，用于协议兼容和连接期占位。
4. 客户端通过 WebSocket 发送 `share.started` 和启动快照元数据。
5. 媒体发布按线路执行：
   - P2P：为每位观看者创建一个发送用 `RTCPeerConnection`；
   - RTC：主引擎发布所选清晰度屏幕，辅助引擎发布 360p 无音频预览；
   - WTN：分别发布预览、高清和语音 StreamID。
6. P2P 由业务服务器转发 Offer、Answer 和 ICE candidate；RTC/WTN 使用各自托管信令。

### 自动预览、高清和最近帧

#### P2P 发送端预览参数

P2P 每个发送端初始使用：

- 最大码率约 300 Kbps；
- 最大帧率 15 FPS；
- 分辨率缩放至约 360p；
- 低网络优先级。

观看端进入房间后会立即为每位共享者请求轻量预览，并持续自动播放，不需要悬浮或点击。RTC/WTN 使用独立预览资源；P2P 调整发送编码参数。页面同时在本地维护最近真实解码帧，用于连接、切换和重连期间防止黑屏。点击画面后才请求高清：

1. 观看者发送 `quality.request`。
2. 服务器验证房间成员关系和共享状态。
3. 共享者调用 `RTCRtpSender.setParameters()`。
4. 只有确认参数生效后，共享者才发送 `quality.ack`。
5. 观看者收到 `quality.confirmed` 后才显示高清状态。

如果参数应用失败，观看者保持预览模式，并收到说明。

### 重连行为

- WebSocket 断开后使用短暂退避自动重连。
- 停止共享时短暂保留最后画面，避免界面闪烁。
- 参与者断开后短暂延迟移除，吸收瞬态网络变化。
- 自动播放的视频约每秒更新一次本地最近帧缓存；切换画面或取消高清时立即抓取当前帧。
- 健康预览始终保持实时播放，最近帧不会冻结正常播放中的低清画面。
- 点击已经冻结的空闲画面仍会重新请求预览或高清，不会因为当前没有 `MediaStream` 而失效。
- 新一次共享使用新的 `startedAt` 缓存键，不会错误复用上一次共享的最后画面。

## 语音流程

语音始终独立于屏幕发布，不同媒体线路使用不同实现：

- P2P：每个方向使用独立语音 `RTCPeerConnection`，复用屏幕共享的 ICE 配置；
- RTC：麦克风使用主引擎 `publishStream(AUDIO)`，屏幕使用 `publishScreen()`；
- WTN：麦克风使用独立语音 StreamID。

1. 用户点击加入语音。
2. 浏览器请求麦克风权限。
3. 采集首选项启用回声消除、降噪、自动增益、单声道和 48 kHz。
4. 服务器广播 `voice.updated`，更新成员列表和静音状态。
5. P2P 建立语音 Peer；RTC 发布主流音频；WTN 发布独立语音流。
6. 本地和远端电平用于说话高亮，不参与媒体转发决策。
7. 静音只停止发送自己的麦克风声音，不退出语音房间。
8. 切换屏幕清晰度不会重建 RTC/WTN 语音发布。
9. 退出语音会停止麦克风采集并释放对应语音连接。

发送端优先选择 Opus，语音发送上限约 48 Kbps，并提高网络优先级。语音轨标记为 `speech`。麦克风意外断开时，客户端会尝试自动切换到系统默认设备。实际能力仍取决于浏览器和硬件。

屏幕系统声音是另一条音频路径：默认关闭，只随高清主屏发布；RTC/WTN 的轻量预览不携带系统音频。麦克风静音不得关闭屏幕系统声音。

## WebSocket 协议

### 客户端到服务器

| 事件 | 用途 |
| --- | --- |
| `room.join` | 加入固定房间 |
| `room.leave` | 离开当前房间 |
| `share.started` | 发布屏幕共享和启动快照 |
| `share.updated` | 更新分辨率、帧率或码率 |
| `share.stopped` | 停止屏幕共享 |
| `signal` | 转发屏幕或语音 SDP/candidate |
| `quality.request` | 请求预览或高清 |
| `quality.ack` | 确认发送端参数是否生效 |
| `voice.updated` | 更新语音参与和静音状态 |
| `ping` | 心跳 |

### 服务器到客户端

| 事件 | 用途 |
| --- | --- |
| `room.snapshot` | 完整成员和共享状态 |
| `participant.joined` / `participant.left` | 成员变化 |
| `share.started` / `share.updated` / `share.stopped` | 屏幕共享变化 |
| `signal` | 转发屏幕或语音 SDP/candidate |
| `quality.request` | 向共享者传递高清或预览请求 |
| `quality.confirmed` | 向观看者返回共享端结果 |
| `voice.updated` | 语音参与和静音变化 |
| `chat.message` | 新聊天消息 |
| `room.error` | 可读房间错误 |
| `session.replaced` | 账号被其他页面或设备接管 |
| `pong` | 心跳响应 |

协议类型定义位于 `src/shared/types.ts`。

## 认证与会话

- 密码使用 Node.js `scrypt` 和随机盐哈希。
- 登录会话使用随机 HttpOnly Cookie。
- SQLite 只保存 token 哈希。
- 会话在 `SESSION_DAYS` 后过期。
- 登录失败按客户端 IP 在内存中限流。
- 每个账号只允许一个活跃浏览器客户端 ID。
- 新登录或新标签页会注销旧客户端并关闭旧 WebSocket。

## 持久化

SQLite 存储：

- 用户；
- 会话；
- 文字消息；
- 为数据库兼容保留的历史附件表。

SQLite 使用 WAL 模式。备份时必须同时处理数据库和 WAL 文件。

## TURN 凭证

配置 `TURN_SECRET` 后：

```text
username = 过期时间戳:userId
credential = Base64(HMAC-SHA1(共享密钥, username))
```

coturn 使用相同规则验证。浏览器只获得短期凭证，不会收到永久 TURN 密码。

共享密钥只属于服务器，不得发送给浏览器或提交到 Git。

## 扩展边界

当前架构适合：

- 小房间；
- 共享者上传带宽足够；
- 大多数客户端可建立 P2P；
- TURN 流量在服务器出口限制内。

出现以下情况时应优先切换 RTC/WTN，或引入独立 SFU：

- 十人房内经常有多人同时共享；
- 多人同时请求高分辨率画面；
- 发送端上传或浏览器编码成为瓶颈；
- TURN 出口成本高于选择性转发。

## 浏览器支持

推荐：

- 桌面 Chrome；
- 桌面 Edge。

部分支持：

- Safari：屏幕和系统音频行为取决于 macOS 版本；
- Firefox：屏幕选择器和系统音频能力因平台而异；
- 移动浏览器：适合观看和聊天，不建议作为主要共享端。
