# 架构设计

[English](ARCHITECTURE.md) | 简体中文

## 设计目标

Together Screen 面向小型可信群体：

- 固定 2～6 人房间；
- 每位参与者使用管理员创建的独立账号；
- 支持多人同时投屏；
- 低码率预览和点击后升级高清；
- 点对点语音；
- 持久化文字聊天；
- 可自托管，不依赖第三方 SaaS。

项目不试图替代大型会议系统或 SFU。

## 整体组件

```text
React 浏览器客户端
├── 房间和聊天界面
├── WebRTC 屏幕连接
├── WebRTC 语音连接
└── WebSocket 信令客户端
          │
          ▼
Fastify 业务服务器
├── 认证和会话
├── 房间成员和容量
├── WebSocket 信令转发
├── 画质请求与确认转发
├── 聊天 REST API
└── SQLite 持久化

STUN / coturn
└── NAT 地址发现和可选媒体中继
```

## 媒体拓扑

项目使用网状拓扑：

```text
A 向 B 和 C 发送屏幕与语音
B 向 A 和 C 发送屏幕与语音
C 向 A 和 B 发送屏幕与语音
```

当房间有 `N` 人时，最多存在 `N × (N - 1)` 条有方向的媒体连接。编码和解码都在浏览器本地完成，业务服务器只承载信令和聊天。

这种方式对小型房间成本最低，但房间扩大后，发送端上传、浏览器编码和 TURN 出口带宽都会快速增加。

## 房间级媒体模式

每个固定房间持久化一个 `mediaMode`：

- `p2p`：现有浏览器 Mesh，必要时使用 STUN/TURN；
- `wtn`：火山引擎 WebRTC 传输网络的发布/订阅传输。

只有管理员可以切换模式，而且只能在没有成员的房间中切换，避免中断正在传输的媒体。

房间同时带有固定成本等级：

| 等级 | 房间容量 | 允许线路 | 最高画质与码率 |
| --- | --- | --- | --- |
| 普通 | 2～3 人 | 仅 P2P/TURN | 720p / 3 Mbps |
| 高级 | 4～5 人 | P2P/TURN 或 WTN | 1440p / 15 Mbps |
| 极致 | 6 人 | P2P/TURN 或 WTN | 2160p / 30 Mbps |

等级限制在服务端校验。普通房即使收到手工构造的 WTN 或高画质请求，也不会接受。

### 火山 WTN 路径

WTN 房间把屏幕预览、屏幕高清和语音发布为三个独立媒体流：

```text
屏幕预览：<room>_<user>_screen_preview_<unique>
屏幕高清：<room>_<user>_screen_hd_<unique>
语音：    <room>_<user>_voice_<unique>
```

发布端为屏幕创建两个 WHIP 风格的 `RTCPeerConnection`：预览流约 360p / 15 FPS / 300 Kbps，高清流使用房间设置的分辨率、帧率和码率。高清档支持 720p、1080p、2K/1440p、4K/2160p 和跟随屏幕，码率上限为 30 Mbps。预览流不依赖 Simulcast RID，因此不要求 WTN 应用支持 RID。观看者进入房间后会为每位共享者自动建立预览订阅并持续播放；点击后新建高清订阅并替换预览。取消聚焦或切换到其他画面时，观看者重新订阅预览，最近一帧只在订阅切换期间覆盖。

双流方案会让共享者额外上传约 300 Kbps 的预览流，但可以把“预览”和“高清”做成确定可切换的两条 StreamID，不受 WTN 单流层级能力影响。屏幕系统声音只随高清流发布；麦克风语音仍使用独立的单条语音流。

Fastify 服务端负责：

- 验证用户所在房间和媒体模式；
- 按屏幕预览、屏幕高清和语音分别登记最新 StreamID；
- 签发订阅资源前验证目标画质或语音流已经发布；
- 生成符合协议要求的 StreamID；
- 签发短期 HS256 WTN JWT；
- 只向浏览器返回 WTN URL 和 Token。

`WTN_APP_KEY` 永远只保存在服务端。停止或替换 WTN 发布者时会销毁媒体资源；预览结束或参与者离开时，订阅端会关闭自己的资源。

## 屏幕共享流程

### 开始共享

1. 共享者调用 `getDisplayMedia()`。
2. 浏览器应用分辨率和帧率限制。
3. 生成一份低分辨率启动快照，用于协议兼容和连接期占位。
4. 客户端通过 WebSocket 发送 `share.started` 和启动快照元数据。
5. 共享者为每个房间成员创建一个发送用 `RTCPeerConnection`。
6. 服务器转发 Offer、Answer 和 ICE candidate。

### 自动预览、高清和最近帧

每个发送端初始使用预览参数：

- 最大码率约 300 Kbps；
- 最大帧率 15 FPS；
- 分辨率缩放至约 360p；
- 低网络优先级。

观看端进入房间后会立即为每位共享者请求低码率预览，并持续自动播放，不需要悬浮或点击。页面同时在本地维护最近真实解码帧，用于订阅建立、低清/高清切换和重连期间防止黑屏；一旦新视频帧到达，最近帧覆盖层立即隐藏。点击画面后才请求高清：

1. 观看者发送 `quality.request`。
2. 服务器验证房间成员关系和共享状态。
3. 共享者调用 `RTCRtpSender.setParameters()`。
4. 只有确认参数生效后，共享者才发送 `quality.ack`。
5. 观看者收到 `quality.confirmed` 后才显示高清状态。

如果参数应用失败，观看者保持预览模式，并收到说明。

### 重连行为

- WebSocket 断开后使用短暂退避自动重连。
- 停止共享时短暂保留最后画面，避免界面闪烁。
- 参与者断开后短暂延迟移除，吸收瞬态网络变化。
- 自动播放的视频约每秒更新一次本地最近帧缓存；切换画面或取消高清时立即抓取当前帧。
- 健康预览始终保持实时播放，最近帧不会冻结正常播放中的低清画面。
- 点击已经冻结的空闲画面仍会重新请求预览或高清，不会因为当前没有 `MediaStream` 而失效。
- 新一次共享使用新的 `startedAt` 缓存键，不会错误复用上一次共享的最后画面。

## 语音流程

语音与屏幕共享复用同一组 ICE 服务器，但每个方向使用独立的 `RTCPeerConnection`。

1. 用户点击加入语音。
2. 浏览器请求麦克风权限。
3. Web Audio 负责输入增益和电平检测。
4. 服务器广播 `voice.updated`。
5. 每位已加入语音的参与者向其他人发送语音 Offer。
6. 远端音频流挂载到隐藏的 audio 元素，并通过 AnalyserNode 检测说话状态。
7. 静音会禁用发送轨道，但不会拆除语音连接。
8. 退出语音会关闭语音连接并停止全部麦克风处理轨道。

音频约束请求回声消除、降噪、自动增益、单声道采集和 48 kHz 理想采样率。实际能力仍取决于浏览器和硬件。

## WebSocket 协议

### 客户端到服务器

| 事件 | 用途 |
| --- | --- |
| `room.join` | 加入固定房间 |
| `room.leave` | 离开当前房间 |
| `share.started` | 发布屏幕共享和启动快照 |
| `share.updated` | 更新分辨率、帧率或码率 |
| `share.stopped` | 停止屏幕共享 |
| `signal` | 转发屏幕或语音 SDP/candidate |
| `quality.request` | 请求预览或高清 |
| `quality.ack` | 确认发送端参数是否生效 |
| `voice.updated` | 更新语音参与和静音状态 |
| `ping` | 心跳 |

### 服务器到客户端

| 事件 | 用途 |
| --- | --- |
| `room.snapshot` | 完整成员和共享状态 |
| `participant.joined` / `participant.left` | 成员变化 |
| `share.started` / `share.updated` / `share.stopped` | 屏幕共享变化 |
| `signal` | 转发屏幕或语音 SDP/candidate |
| `quality.request` | 向共享者传递高清或预览请求 |
| `quality.confirmed` | 向观看者返回共享端结果 |
| `voice.updated` | 语音参与和静音变化 |
| `chat.message` | 新聊天消息 |
| `room.error` | 可读房间错误 |
| `session.replaced` | 账号被其他页面或设备接管 |
| `pong` | 心跳响应 |

协议类型定义位于 `src/shared/types.ts`。

## 认证与会话

- 密码使用 Node.js `scrypt` 和随机盐哈希。
- 登录会话使用随机 HttpOnly Cookie。
- SQLite 只保存 token 哈希。
- 会话在 `SESSION_DAYS` 后过期。
- 登录失败按客户端 IP 在内存中限流。
- 每个账号只允许一个活跃浏览器客户端 ID。
- 新登录或新标签页会注销旧客户端并关闭旧 WebSocket。

## 持久化

SQLite 存储：

- 用户；
- 会话；
- 文字消息；
- 为数据库兼容保留的历史附件表。

SQLite 使用 WAL 模式。备份时必须同时处理数据库和 WAL 文件。

## TURN 凭证

配置 `TURN_SECRET` 后：

```text
username = 过期时间戳:userId
credential = Base64(HMAC-SHA1(共享密钥, username))
```

coturn 使用相同规则验证。浏览器只获得短期凭证，不会收到永久 TURN 密码。

共享密钥只属于服务器，不得发送给浏览器或提交到 Git。

## 扩展边界

当前架构适合：

- 小房间；
- 共享者上传带宽足够；
- 大多数客户端可建立 P2P；
- TURN 流量在服务器出口限制内。

出现以下情况时应考虑 SFU：

- 房间经常超过 6～10 人；
- 所有人都共享高分辨率画面；
- 发送端上传或浏览器编码成为瓶颈；
- TURN 出口成本高于选择性转发。

## 浏览器支持

推荐：

- 桌面 Chrome；
- 桌面 Edge。

部分支持：

- Safari：屏幕和系统音频行为取决于 macOS 版本；
- Firefox：屏幕选择器和系统音频能力因平台而异；
- 移动浏览器：适合观看和聊天，不建议作为主要共享端。
